# Errors

- Domain and use cases: expected business failures return `Result`; no exceptions (see `use-cases.md`).
- Infrastructure faults: a dedicated, package-private `RuntimeException` per failure kind (`EventPublicationException`, `NatsProvisioningException`, `MissingDatabaseSettingsException`), with an actionable message and the original exception as `cause` whenever there is one.
- Catch only what can actually be thrown and handled: name the types (`IOException | JetStreamApiException | JacksonException`). Never `catch (Exception)` or `catch (RuntimeException)`, except at the isolation boundaries below.
- Telemetry isolation boundary: recording telemetry (business metrics in `BusinessMetricsRecorder`) may catch `RuntimeException` per metric, because it runs user-declared lambdas and Micrometer registration inside the business call or its after-commit callback. It logs one WARN with `frappe.metric`, `frappe.event_type`, `frappe.event_id` and skips that metric; telemetry never fails or reaches the business caller.
- Localization isolation boundary: `LocaleChainResolver` may catch `RuntimeException` around each locale port (`UserLocalePreference`, `TenantLocaleDefaults`), because the ports run another module's arbitrary code on every request, health checks included. A failure counts as "no value" for that link (a failing tenant lookup means every supported language is enabled), is logged once per request at WARN with `frappe.locale_link` (`user_preference`, `tenant_defaults`) and the cause, and the chain continues; localization never fails a request. No other code uses these two boundaries.
- HTTP boundary: `ProblemBoundaryFilter` (right inside the HTTP server observation) catches whatever the filters and the dispatcher throw, unwraps `ServletException`s and hands it to Spring MVC's exception resolvers without rethrowing, so the servlet container never logs it or renders its own page; `ProblemAdvice` (`@ExceptionHandler(Exception.class)`) answers it, and `ProblemErrorController` answers error dispatches (statuses sent with `sendError`). Controllers and filters never catch to answer; they let it propagate. The client gets the generic `internal-error` problem (500) with nothing of the cause; `UnexpectedFailures` logs it exactly once in the whole application, at ERROR, with the cause (ECS `error.*`), `http.request.method` and `url.path` (the original path on error dispatches; the trace id is automatic), counts `http.server.unexpected.errors{error=<simple name of the cause behind servlet wrappers, or "anonymous">}` and attaches the cause to the request's observation (`http.server.requests`, tag `exception`).
- Client faults are not failures of ours (`ClientFaults`): a request body that cannot be read (truncated, malformed, broken chunking: `HttpMessageNotReadableException`, Tomcat's `BadRequestException`) is the 400 invalid-request problem; a client that went away (Tomcat's `ClientAbortException`, `AsyncRequestNotUsableException`) gets no answer. Neither is logged at ERROR or counted. A bare `IOException` never counts as the client's (database drivers throw them too).
- Expected failures at the web edge: a route turns a failed `Result` into `RequestRefusedException` (`result.orElseThrow(RequestRefusedException::new)`), the one exception thrown for an expected failure. It is never logged as an error: `ProblemAdvice` answers it with the problem the module's `ProblemMapper` maps it to (`http-api.md`, "Errors"); only a failure without a mapper, or with a key missing from the catalogs (`NoSuchMessageException`, caught there by name), is treated as unexpected.
- Infrastructure failures are never visible to API clients. A provider adapter (mail, and every future external provider) translates the provider's exceptions into our own sanitized exception (never recipient addresses, bodies, codes or credentials in it) and counts the outcome in a metric; the one boundary that handles the failure logs it once at ERROR. Anything unexpected reaching the web layer becomes the generic, localized 500 problem (HTTP boundary above), never provider names, messages or stack traces. Mail:
  - Transient (Resend 5xx, 401/403/408/409/429 and configuration errors such as `invalid_from_address` under any status, network; SMTP 4xx, any 5xx other than a refused recipient such as 530, connection): the transport throws `MailDeliveryException`; `ObservedMailer` records `mail.send` with `mail.outcome=failed` and `error` and rethrows without logging. The listener (`@ApplicationModuleListener`, async) fails and Spring's async boundary logs one ERROR with the exception; the outbox retries (each resubmission is async too, so it logs at the same boundary). One ERROR per failed attempt, pinned by `MailOutboxIntegrationTests`.
  - Permanent (Resend other 4xx such as 400/422 validation or invalid recipient; SMTP 5xx reply to RCPT TO, `SMTPAddressFailedException`, only): the transport throws the package-private `MailRejectedException`; `ObservedMailer` is its handling boundary: one ERROR (`frappe.mail.template`, `frappe.mail.provider`, `frappe.mail.locale`), `mail.outcome=rejected`, and it returns normally so the publication completes. Not dead-lettered: listeners run asynchronously, so the outbox never sees the exception (resubmission only hands the event over) and Modulith keeps no failure cause; retrying a rejected request cannot succeed, and the ERROR plus the counter make it visible.
- A provider's own error text is not chained as the cause when it can echo the request (Resend error bodies, SMTP replies quoting the recipient): the exception keeps the status and error name only. Network failures keep their `IOException` cause.
- Log OR rethrow, never both. Log once, at the boundary that handles the failure and knows the context (a background task, a listener turning a failure into a failed future). Everything below it wraps and rethrows.
- `InterruptedException`: restore the flag (`Thread.currentThread().interrupt()`), then finish cleanup (close resources) before returning.
- No shared base exception while the exceptions are package-private; add one only when a caller outside the package needs to catch the family.
- Public exceptions are the exception to package-private: only when another module must catch them, declared in the platform kernel package next to the port that throws them (`SecretStoreUnavailableException` for `ShortLivedSecretStore` and `RateLimiter`, `MailDeliveryException` for `Mailer`).
- A boundary that turns a failure into a result (e.g. a failed `CompletableFuture`) is where it is logged. Frameworks may log the same failure again (Spring Modulith's INFO for failed listeners); that duplicate is known and accepted.
- Wrap third-party signals at the adapter boundary: jnats' `IllegalStateException` for a closed connection becomes `NatsUnavailableException` in `NatsClient`.
- Fail fast at startup for missing configuration, naming the environment variable to set — except when the missing configuration is an optional external capability with a documented "unavailable" outcome, not a hard dependency: no `FRAPPE_DEEPL_API_KEY` does not fail startup, `MachineTranslator.isAvailable()`/`MachineTranslationGlossaries` just report/throw "unavailable" until a key is configured (`i18n.md`, "Machine translation on demand").
- Sanitizing a third-party adapter boundary (a provider's failures must never reach a caller with the provider's name or response, e.g. `DeepLMachineTranslator`/`DeepLGlossaries`): map every provider exception to our own dedicated exception with the provider failure only as `cause`, but do **not** log there — that would violate "log OR rethrow, never both" a second time, once at the adapter and once at the real boundary. The adapter only tags its own telemetry (an `Observation`'s `outcome` key value) with what happened; logging happens once, at the boundary that actually handles the failure (the web layer's catch-all, or a caller's own boundary), which already knows the request context worth logging.
- Stored events that no longer load (outbox rows of an older deployment): a missing class surfaces as `ClassNotFoundException` from `ClassUtils.forName`, and Modulith 2.1.1's `JacksonEventSerializer.deserialize` (an unwrapped `ObjectReader.readValue`) throws Jackson 3's `JacksonException` for JSON that no longer fits the class. Handle both per row (`PublicationRedelivery`) so one row never aborts a batch; catch those types, not `RuntimeException`.
- `HandlerMappingGuard` catches `Exception` around `HandlerMapping#getHandler`, which declares it: a mapping that cannot answer may serve the request, so the security decision fails closed (the request is refused). Nothing is logged; the caller gets 401/403.
- The other allowed `catch (RuntimeException)`: `PublicationRedelivery` around `TransactionalApplicationListener.processEvent`, because listener code is arbitrary and one failing listener must not abort the recovery batch (Modulith's own resubmission catches the same way). It marks the row failed and logs once. `ResendMailTransport` catches `RuntimeException` only to unwrap the SDK's bare `RuntimeException(IOException)` for network failures into `MailDeliveryException`; anything else is rethrown untouched. Any broad catch beyond those listed here is rejected in review; the outbox recovery pass catches only `DataAccessException`.
- Scheduled task actions (`scheduling.md`) throw; they never catch to log. The scheduler is the boundary: it records the error on `scheduled.task`, logs it once and retries with backoff. Scheduling calls throw the kernel's `TaskSchedulingException` (database unreachable, or an entity's run in progress); catch it where a caller can handle it (`OutboxRecoveryTrigger`). db-scheduler's own exceptions (`TaskInstanceCurrentlyExecutingException`, `TaskInstanceNotFoundException`, the shaded `SQLRuntimeException`, which is not a `DataAccessException`) never leave `platform.infrastructure.scheduling`.
