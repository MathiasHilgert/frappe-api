# Internationalization

Frappé speaks English, Spanish and Portuguese. Public API: `com.frappe.platform.i18n` (`Messages`, `SupportedLocales`, `UserLocalePreference`, `TenantLocaleDefaults`, `TenantLocales`). The kernel exposes plain Java only (`I18nKernelDependenciesTest` enforces it); Spring (`MessageSource`, `MessageSourceAccessor`, `LocaleResolver`) and ICU4J live in `platform.infrastructure.i18n`. Modules depend on the kernel types only.

## Which language a request gets

- Supported locales are `en`, `es`, `pt` (`SupportedLocales`). ICU4J's `LocaleMatcher` maps what is asked for onto them with CLDR language distance: `es-AR` → `es`, `pt-BR` → `pt`, `fr` → no match. CLDR also maps Catalan, Galician, Basque, Guarani and Quechua (`ca`, `gl`, `eu`, `gn`, `qu`) to `es`, their closest supported language; accepted. Enabled languages are matched the same way (`pt-BR` enables `pt`).
- The chain (`LocaleResolver` bean `localeResolver`, resolved once per request): the authenticated user's preferred locale → `Accept-Language` (quality weights honoured, malformed headers ignored) → branch default → business default → `en`. Anonymous (diner) requests have no preference, so they start at `Accept-Language`.
- With a business context every link is matched only against the business's enabled languages; a link outside them is skipped. The chain always ends in a supported locale, `en` last.
- Every response carries `Content-Language` (the resolved locale) and `Vary: Accept-Language`, error responses included, so caches never serve one language to a client asking for another.
- Localization never fails a request: a port that throws counts as "no value" for its link (a failing tenant lookup enables every language), logs one WARN with `frappe.locale_link`, and the chain continues (`errors.md`, localization isolation boundary).
- Hooks: identity implements `UserLocalePreference`, organization implements `TenantLocaleDefaults` (enabled languages, business default, optional branch default), each as one bean in its `infrastructure`. They take no arguments: the platform asks at most once per request, on the request's thread, after Boot's `RequestContextFilter` and before security filters, so the implementation reads the current request (session token, or the branch a diner browses) through `RequestContextHolder` in its own web adapter. Until they exist, every request is anonymous and all three languages are enabled.
- In a request, `Messages.get(key, args...)` resolves in the chain's locale. Outside one (listeners, jobs, emails), use `Messages.get(locale, key, args...)` with the recipient's locale. Never use the JVM default locale.

## Catalogs

- One set per module: `src/main/resources/i18n/<module>/messages_en.properties`, `messages_es.properties`, `messages_pt.properties`, UTF-8 (write `á`, not `á`).
- Keys: `<module>.<subject>.<detail>`, lowercase, dot-separated, kebab-case words (`order.tab.already-closed`). The module prefix is mandatory: all catalogs share one message source. Problem text uses keys in the same namespace (see "Errors").
- Add, rename or remove a key in all three catalogs in the same commit. Static strings are translated by hand in the catalogs: no TMS, no machine translation. A `#` comment above a key gives translators context when the English is ambiguous.
- Resolve text through the injected kernel port `Messages`; never hard-code user-facing strings. Every user-facing string comes from a catalog, or it cannot be translated.

```java
@Component
class ReceiptTexts {
    private final Messages messages;                      // com.frappe.platform.i18n.Messages

    ReceiptTexts(Messages messages) {
        this.messages = messages;
    }

    String itemCount(int count) {
        return messages.get("order.items", count);        // request locale: "2 items" / "2 artículos" / "2 itens"
    }

    String subject(Locale recipient, String tab) {
        return messages.get(recipient, "order.receipt.subject", tab);   // outside a request
    }
}
```

- An unknown key throws, naming the key, the locale and the catalog files to edit; it is a bug, never caught.
- Key safety comes from the catalog check (below) and the IDE, not from generated code: IntelliJ groups each module's `messages_en/es/pt.properties` into one resource bundle (Resource Bundle Editor: the three languages side by side, missing translations highlighted, a key renamed in all three files). Code generation for keys is deliberately not used: it would be our own tooling without a proven need.

## ICU MessageFormat

Messages are ICU MessageFormat (v1 syntax), formatted by ICU4J for every call, with or without arguments.

- Arguments are numbered (`{0}`, `{1}`), because Spring's `MessageSource` (behind `Messages`) passes an array; named arguments fail the check.
- Plurals: `{0, plural, one {# item} other {# items}}`. Always give `other`; use `=0` for a special zero text. CLDR rules differ per language (Portuguese treats 0 and 1 as `one`), so each catalog states its own forms.
- Select for enums and variants: `{0, select, dine_in {at the table} other {to go}}`.
- Quoting: `'{'` and `'}'` produce literal braces; `''` is one apostrophe. A lone apostrophe in prose (`don't`) stays literal.
- One message is one complete sentence: pass values as arguments, never concatenate messages or fragments (word order differs between languages).

## Checks

- `./gradlew check` (`ShippedMessageCatalogsTest`) and application startup verify every catalog on the classpath: the same key set in each module's three catalogs, keys inside the module's namespace (or problem detail codes of its own exceptions), only `en`/`es`/`pt` catalogs, and every message valid ICU with numbered arguments. Each violation names the catalog path (module and locale) and the key; startup fails listing all of them.
- Tests prove text comes from a catalog with the pseudo-locale en-XA (`SupportedLocales.PSEUDO`, with `Messages.get(SupportedLocales.PSEUDO, key, args...)`): it resolves the English catalog accented and bracketed (`Hello, {0}!` → `[Ĥéĺĺó, Ana!]`); a hard-coded string stays plain.

## Errors (problem details)

Problem text comes from the catalogs, never from an exception (`http-api.md`, "Errors"):

- A module's business failures: its `ProblemMapper` names a message key in the module's namespace; the catalogs hold `<key>.title` and `<key>.detail`, the detail taking the problem's params as `{0}`, `{1}`… in order.
- Framework and security failures: platform text per status, `platform.problem.<slug>.title|detail` (`i18n/platform`), and `platform.validation.<constraint>` for validation errors.

```properties
# i18n/order/messages_es.properties
order.tab.already-closed.title=Cuenta ya cerrada
order.tab.already-closed.detail=La cuenta {0} ya está cerrada.
```

- Spring's per-exception codes (`problemDetail.title.<FQCN>`) are not used for API problems: Spring raises several exception classes per status, each with its own code, and a missing one silently keeps Spring's English text. The catalog check still accepts them for a module's own exceptions; `problemDetail.type.*` is rejected: problem types are stable URIs set in code, never translated.
- The problem is resolved in the locale the chain resolved for the request, including for refusals of the security chain, which run before Spring MVC.

## The API returns raw values

Clients format for their own locale and device; the API never returns a formatted value.

- Money: minor units plus the ISO 4217 code (`{"amount": 1250, "currency": "BRL"}`).
- Instants: RFC 3339 in UTC, plus the branch's zone id (`"America/Sao_Paulo"`) wherever local time matters.
- Enums as stable codes (`dine_in`), never as labels.
- Server-side formatting happens only for emails and receipts, with ICU4J in the resolved locale (no Moneta/JSR 354).

## Tenant content (menus, item names, descriptions)

Tenant content is data, not catalog text. The entity tables and the translation module come later; these are the conventions they follow.

- One translation table per translatable entity in the owning module's schema (`<module>.<entity>_translation`): the entity id, `tenant_id` (with RLS like every tenant table), `locale`, one column per translatable field, and per row:
  - `origin`: `SOURCE` (written in that language), `MACHINE` (machine translated), `HUMAN` (translated by a person);
  - `status`: `DRAFT`, `NEEDS_REVIEW`, `APPROVED`;
  - `source_digest`: a digest of the source-language values the translation was made from; when the source changes and the digest no longer matches, the translation is stale and goes back to `NEEDS_REVIEW`.
- Reading falls back per field over the locale chain: each field takes the value of the first locale in the chain that has it, down to the source language, so a missing translation of one field never blanks the whole entity.
- Tenant content is translated by its owner, or at the owner's request through the translation module. It is never translated automatically, and machine output is marked as such to diners (responses carry the field's `origin`).
