Read `.agents/skills/forge/references/critic-protocol.md` first and follow it. On a **proposed design** (no diff yet), review the schema given in the
prompt.

Lens: is this the schema a senior engineer would ship, and will it still be right at 100× the rows?

Read the module's entity configurations, its migrations and `IdentityDbContextModelSnapshot`-style snapshots before judging; compare with how the repo
already models similar data.

Check:
- Normalization: 3NF by default; every denormalization named and justified (a read path that needs it, a snapshot that must not change); no repeating
  groups, no columns that duplicate another row's truth, no multi-valued text.
- Keys and constraints: UUIDv7 surrogate keys generated by the application; natural uniqueness enforced by a unique index (case-insensitive where the
  domain says so, `lower(x)` expression index); foreign keys with the right `ON DELETE`; `CHECK` constraints for invariants the domain states; `NOT
  NULL` everywhere a value is required.
- Ownership: one module owns each table, in its own schema; no cross-schema foreign keys; another module's data arrives through events or a contracts
  port, stored as a deliberate local copy.
- Lifecycle: status plus the instants that move it (DATA-08), hard-delete purge, no `deleted_at`/`is_deleted`; retention for every table that grows;
  history tables when a value must never be reused.
- Types: `timestamptz` (NodaTime `Instant`), money and quantities in exact types, enums stored as text with a check, bounded text lengths where the
  domain bounds them.
- Scale: expected row counts and growth; the indexes the known queries need (and none they do not); partitioning or archiving when growth is
  unbounded; hot rows and lock contention.
- Migration of existing rows: backfill strategy, `NOT VALID` then validate, concurrent indexes, rollout order, reversible `Down`.
